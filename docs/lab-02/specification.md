# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Deliver a responsive, Requester-facing IT support ticketing MVP for TokTickIT using a temporary Development Requester selection mechanism for user context. Requesters can create tickets with attachments, view and filter their owned tickets, inspect ticket details, and manage attachments with soft-removal rules under strict ownership protection and a consistent Zen Green design system.

## 2. Stakeholder Request Interpretation
The IT department needs a user-friendly system for staff to submit, search, and manage support requests. Because full authentication will be implemented in Sprint 3, Sprint 2 requires a temporary "Development Requester Selector" to simulate user context. The application must enforce ticket ownership, issue backend-generated ticket numbers, allow permitted attachment uploads and soft removals, and maintain visual consistency following the Zen Green theme across desktop, tablet, and mobile viewports.

## 3. Scope

### Included
- Development Requester selection screen and requester context switcher.
- IT support ticket creation (Category, Related System, Requested Priority, Ticket Summary, Description, Attachments).
- Backend generation of unique Ticket Numbers (`TKT-YYYY-XXXXXX`).
- My Tickets paginated list screen with search, multi-filter, sorting, clear filters, and empty/no-results states.
- Ticket Detail view (read-only ticket information and attachment list).
- Attachment lifecycle: upload (JPG, PNG, WEBP, PDF up to 5MB, max 5 active), download active files, and soft removal with mandatory reason logging.
- Strict requester ownership enforcement for tickets and attachments (preventing unauthorized access).
- Zen Green UI component design system and responsive layout rules.

### Excluded
- Real user authentication, passwords, sessions, JWT, or role-based auth (handled in Lab 3).
- IT Staff workflow (claiming, reassigning, changing status or IT priority).
- Public comments, internal notes, and Actions Taken audit history.
- Post-creation ticket lifecycle status changes (resolving, closing, reopening).
- Admin management interfaces.

## 4. Functional Requirements
- **FR-01**: The system shall allow the user to select an active Development Requester to establish the current session context.
- **FR-02**: The system shall display the selected Requester's identity in the top application header with an option to change/switch requesters.
- **FR-03**: The system shall provide a Create Ticket form capturing Category, Related System, Requested Priority, Summary, Description, and Attachments.
- **FR-04**: The system shall validate mandatory fields on both frontend and backend, returning clear field-level error messages.
- **FR-05**: The backend shall auto-generate a unique Ticket Number formatted as `TKT-YYYY-XXXXXX` upon ticket submission.
- **FR-06**: New tickets shall be assigned initial status `NEW` and default IT Priority `MEDIUM`.
- **FR-07**: The system shall allow uploading attachments matching allowed types (JPG/JPEG, PNG, WEBP, PDF) up to 5 MB per file and maximum 5 active attachments per ticket.
- **FR-08**: The system shall display "My Tickets" listing only tickets belonging to the currently selected Requester.
- **FR-09**: "My Tickets" shall support text search across Ticket Number and Summary.
- **FR-10**: "My Tickets" shall support filtering by Category, Requested Priority, IT Priority, and Current Status.
- **FR-11**: "My Tickets" shall support column sorting (Ticket Number, Ticket Date, Last Updated) and page pagination.
- **FR-12**: The system shall display a read-only Ticket Detail view showing all fields and attached files.
- **FR-13**: The system shall allow downloading active attachments belonging to owned tickets.
- **FR-14**: The system shall allow soft-removing an attachment from an owned ticket upon providing a non-empty removal reason.
- **FR-15**: The system shall block removed attachment download and preview while keeping file metadata visible in the attachment list with a "Removed" indicator and removal reason.

## 5. Business Rules
- **BR-01**: Official Ticket Number is generated by the backend upon creation and must be unique.
- **BR-02**: Every new ticket begins with `currentStatus = NEW` and `itPriority = MEDIUM`.
- **BR-03**: The Development Requester selection is a testing context simulator only, not secure authentication.
- **BR-04**: Requesters can only access, view, search, download, or modify tickets and attachments that they own (`requesterId` match). Access to tickets owned by other requesters returns HTTP 403 Forbidden or 404 Not Found.
- **BR-05**: Inactive Development Requesters (`isActive = false`) must not appear in the Requester selector and cannot create tickets.
- **BR-06**: Permitted attachment MIME types are `image/jpeg`, `image/png`, `image/webp`, and `application/pdf`. Other file types are rejected with HTTP 400.
- **BR-07**: Maximum file size for any single attachment is 5 MB (5,242,880 bytes). Oversized files are rejected.
- **BR-08**: A ticket can have at most 5 active (`isRemoved = false`) attachments at any time.
- **BR-09**: Attachment removal is implemented strictly as a soft-removal (`isRemoved = true`, recording `removedAt` timestamp and `removedReason`). File binary data remains untouched or safely archived.
- **BR-10**: Soft-removed attachments cannot be downloaded or previewed (`GET /api/attachments/:id/download` returns HTTP 404/403). Metadata remains visible to the owner.
- **BR-11**: If form validation fails on ticket submission, entered values must be retained in the form without loss.
- **BR-12**: Switching the Development Requester automatically clears existing ticket state and reloads data for the newly selected requester.
- **BR-13**: Summary must be between 5 and 150 characters. Description must be between 10 and 2000 characters.
- **BR-14**: When search or filter criteria return no matching tickets, a dedicated "No matching tickets found" empty state is displayed with a "Clear Filters" action.
- **BR-15**: When a requester has zero total tickets created, a dedicated "No tickets yet" empty state is displayed with a "Create Ticket" primary action.

## 6. UI Specification Summary
- **Color Tokens**:
  - Primary Green: `#006B3C` (Header background, primary buttons)
  - Secondary Green: `#0B7A46` (Active tabs, focus rings, links, hover states)
  - Pale Green: `#EAF6EF` (Selected items, success callouts, subtle backgrounds)
  - Page Background: `#F5F7F6` (Quiet light neutral)
  - Surface/Cards: `#FFFFFF` with 1px `#E2E8F0` border and light box shadow
  - Text Primary: `#1A2E22` (High contrast charcoal-green)
  - Error: `#B91C1C` (Dark red text and border)
  - Warning: `#D97706` (Amber callouts & badges)
  - Success: `#15803D` (Green badges & text)
- **Responsive Layout**:
  - Desktop (>= 992px): Multi-column grid, max content width 1200px centered.
  - Tablet (768px - 991px): 2-column layout where summary/description receive flexible width.
  - Mobile (< 768px): Single column vertical stack, touch-friendly tap targets (>= 44px), responsive table turns to card stack.

## 7. Data Changes
- **Prisma Models**:
  - `RequesterUser`: `id`, `name`, `email`, `department`, `isActive`, `createdAt`.
  - `Category`: `id`, `name`, `createdAt`.
  - `RelatedSystem`: `id`, `name`, `code`, `isActive`, `createdAt`.
  - `Ticket`: `id`, `ticketNumber`, `requesterId`, `categoryId`, `relatedSystemId`, `summary`, `description`, `requestedPriority`, `itPriority`, `currentStatus`, `ticketDate`, `updatedAt`.
  - `Attachment`: `id`, `ticketId`, `filename`, `originalName`, `mimeType`, `fileSize`, `storagePath`, `isRemoved`, `removedAt`, `removedReason`, `uploadedAt`.
  - **Enums**: `Priority` (`LOW`, `MEDIUM`, `HIGH`, `URGENT`), `Status` (`NEW`, `OPEN`, `IN_PROGRESS`, `PENDING`, `RESOLVED`, `CLOSED`).

## 8. API Contract Summary
- `GET /api/requesters` - List active requesters.
- `GET /api/categories` - List active categories.
- `GET /api/related-systems` - List active related systems.
- `POST /api/tickets` - Create new ticket for requester.
- `GET /api/tickets` - List owned tickets (with search, category, priority, status, sort, page, limit).
- `GET /api/tickets/:id` - Get detail of owned ticket.
- `POST /api/tickets/:id/attachments` - Upload attachment to ticket.
- `GET /api/tickets/:id/attachments` - List attachment metadata.
- `GET /api/attachments/:id/download` - Download active attachment file.
- `PATCH /api/attachments/:id/soft-remove` - Soft-remove attachment with reason.

## 9. Acceptance Criteria
- **AC-01**: Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed on the success screen.
- **AC-02**: Given no Development Requester is selected, when the user attempts to open My Tickets or Create Ticket, then the Requester Selection modal/screen is displayed.
- **AC-03**: Given Requester B is selected, when a Ticket belonging to Requester A is requested via API or UI, then HTTP 403/404 is returned and data is not shown.
- **AC-04**: Given an invalid file type (e.g. .exe), when uploaded as an attachment, then submission is blocked with an error message "Allowed file types: JPG, PNG, WEBP, PDF".
- **AC-05**: Given an attachment larger than 5 MB, when uploaded, then submission is blocked with an error message "File size must not exceed 5 MB".
- **AC-06**: Given a ticket with 5 active attachments, when uploading a 6th attachment, then submission is blocked with message "Maximum 5 active attachments per ticket reached".
- **AC-07**: Given a valid attachment soft-removal request with reason, when submitted by ticket owner, then attachment `isRemoved` becomes true, metadata remains visible with "Removed" badge and reason, and download button is disabled.
- **AC-08**: Given search term "VPN", when entered in My Tickets search input, then only tickets matching "VPN" in Ticket Number or Summary are returned.
- **AC-09**: Given active requester switching from User A to User B, then My Tickets automatically reloads showing only User B's tickets.
- **AC-10**: Given form input with missing Summary, when user clicks Submit Ticket, then inline field validation error "Summary is required" is displayed and form submission is prevented.

## 11. Assumptions and Decisions
- **Decision 1**: Session storage / Local storage is used to store the selected Development Requester ID on the client side. `X-Requester-Id` header is passed with API requests to identify the acting requester.
- **Decision 2**: File uploads are stored locally in `server/uploads/` with unique filenames (`attachment-<timestamp>-<uuid>.<ext>`) to prevent filename collisions.
